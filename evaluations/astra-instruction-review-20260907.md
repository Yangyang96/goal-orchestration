## 对强模型的约束方式

- 规定需要实现什么、哪些边界不能改变、什么证据可以验收，不替模型逐步编排实现。
- 能自主决定的事项直接做；澄清和批准分别处理，并沿用上下文中已给出的答案。
- 不因次数、字数、检查点或子任务边界停下，也不在没有新依据时机械重复尝试。
- 以用户要求的完整交付为完成标准；不把额外重构、文档、提交或审查变成默认目标。

入口新增了原版缺失的决策边界，因此正文有所增加；同时删除了微观格式和
流程配额。此处优先保证决策清晰，没有声称减少 token 或提高某个模型的实测成功率。

### 独立决策推演结果

评估者：`skill_behavior_review`，不继承本次主线程审阅历史，只接收当前 Skill、
原始场景及只读评估要求。九个场景均得到可判定的下一步，未发现必须修改
才能处理这些场景的冲突。

| 场景 | 推演得到的动作及完成边界 |
|---|---|
| 小 CSS 溢出，无其他交付指令 | 直接修复并验证受影响视图；不自动增加 Agent、状态文件、worktree 或提交 |
| 已授权 commit、push 和 draft PR | 沿用授权执行三项交付；本地检查或提交成功不代表整个任务完成 |
| 第四次失败，新日志提供新假设 | 继续验证新假设；不因次数申请批准；仍受用户范围和预算限制 |
| 必须兼容旧 API，破坏性迁移授权未说明 | 先调查并实现兼容路径；仅在确需改变已明确契约时才准备方案并提问 |
| 子 Agent 代码未变，但集成共享接口变化 | 复用不受影响的证据；重跑接口变化影响的组件及组合检查 |
| 任务依赖 dirty 改动，默认 worktree 位置不可写 | 在原工作区串行推进并保留用户改动；未要求隔离就不为目录权限停住任务 |
| 实现已通过，必需部署缺凭据 | 先查可用授权配置并完成部署准备；确需用户配置时再提问；部署仍是未完成项 |
| 状态记录与用户新要求冲突 | 当前明确要求优先，更新陈旧记录和验收证据；不要求重认旧计划 |
| 要求明天无人值守但没有后台能力 | 保存准确下一步，披露无法自动续跑；不能声称已安排，也不能把写状态当作完成 |

评估仍依赖模型在实际项目中正确调查事实。兼容迁移是否存在可行路径、
凭据是否能从已授权配置获取，都必须由具体环境证据决定；Skill 不预设答案。
本轮没有执行真实部署、调度或跨运行恢复，也没有进行 GPT-6 Astra 的性能 A/B 实验。
