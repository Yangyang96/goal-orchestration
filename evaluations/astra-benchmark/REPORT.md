# Astra Skill 三组对照实测

日期：2026-09-07。状态：全部正式执行完成。

测试后按用户要求关闭自动调用，改为仅由用户主动开启。本报告及归档仍记录测试时冻结的版本；自动发现/调用策略不在本轮行为对照范围内。

## 结论

本次没有证明加载 goal-orchestration 能让 Astra 比不加载它更有效。原生和新版都完成主测试的 6/6 个任务，跨会话续接均为 2/2；旧版主测试为 5/6。旧版的一次缺口是功能已完成但没有交付要求的本地 commit。新版相对旧版的结果是有利信号，单次差异不足以确定由哪条规则造成，也不能证明稳定提升。

建议保留优化后的规则作为按需使用的协调规范，不把它设为所有普通开发任务的默认增强层。规则更清楚有维护价值；本轮实测没有验证相对原生 Astra 的额外完成率收益。多写者协作、大型项目集成和复杂恢复仍未覆盖，不能据此断言该 Skill 在所有场景都无效。

## 怎么测

- 执行参数：`gpt-6-astra`、`xhigh`，`codex-cli 0.153.2`，Python 3.14.6、SQLite 3.53.3。模型参数由 CLI 明确指定；后端内部权重版本没有额外可核验接口。
- 三组：不加载本 Skill；加载 Git `7845565` 的旧版；加载测试前冻结的仓库优化版。新版入口 SHA-256：`97da725b78ed5c4def1c5c06b3740afef325a39fb453b711330494860d8bdd9c`。
- 每种任务每组重复两轮；两执行槽、固定随机种子排序，每次进程最多 360 秒。全部正式执行均在时限内结束。
- 独立 Agent 在未读取两版 Skill 的情况下编写夹具；先验证初始缺陷会失败、参考修复会通过。执行模型只得到任务源代码、需求和指定 Skill，不得到隐藏判卷器或参考实现。
- 使用全新工作目录；续接阶段只继承同一工作树，不传入上一阶段聊天。第二阶段接口只在第一阶段请求中给出，由模型自行决定怎样保留。
- 隐藏检查运行真实 API、CLI、SQLite 和 Git；另由独立 Agent 审阅隐藏组别标签的日志及文件快照。叙述或引用文本可能暴露身份，因此这是隐藏标签审阅，并非严格双盲或人工评审。
- 全程保留公共 Codex 约束，禁用额外用户 Skill、插件和执行模型的子 Agent。通过临时 CLI 参数调整，没有修改已安装 Skill 或全局配置。读取隔离依靠权限与指令，不能宣称为硬隔离；可见日志未发现读取其他候选或全局 Skill。

正式执行共 36 次：原始 18 次、续接 12 次、交付重跑 6 次。有效主比较使用原始普通/数据库任务 12 次及交付重跑 6 次；续接另外单列。原始受公共 Git 权限限制的 6 次交付全部保留，未混入主比较。校准、夹具编写、审阅和汇总不计入这 36 次。

## 自主性、澄清、批准与完成

所有有效样本的功能检查均通过。独立审阅没有确认多余澄清、重复确认、虚报完成、破坏用户草稿或明显越界扩展。续接记录使用不同文件格式均可通过，没有按 Skill 术语、文件名或固定措辞给分。

唯一完整交付缺口为 `delivery-corrected/01-delivery-old-r1`：代码、文档和 22 项自写测试完成，未创建本地 commit。最终说明如实披露阻塞，不能判为虚报完成。同期 sandbox 拒绝有日志，但部分 CLI 事件遗漏，不能断言它从未申请权限或确知审批被拒的具体原因。

相同审批设置下，新版两轮、原生两轮和旧版另一轮均完成提交。新版首轮日志显示遇到 `.git/index.lock` 写入限制后使用平台审批继续，成功提交恰好 5 个任务文件，保留未提交草稿。这证明该配置存在正常完成路径，也使旧版的单次缺口成为应保留的实际交付差异；它不构成规则因果证明。

审阅还记录了正常的测试断言修正与恢复时基线复跑。出现中间失败本身不是停止或过度工程；这些操作均未造成额外用户确认或未完成功能。测试中没有必须向用户澄清的缺失业务决定，因此不能证明 Skill 能正确识别所有“应当提问”的情况。

## 权限修正与保留的失败

原始非交互模式不允许 Git 写入所需的权限升级，6 次交付都完成了功能但没有 commit。校准后，整层交付任务在新目录统一用 `--approve-for-me` 重跑，仍保留 workspace-write 与自动审批，没有使用绕过沙箱的模式。新版/原生的成功提交及校准记录说明修正后有可用路径；修正后的旧版单次失败未被再次排除。

原始受限运行如下，每次均有 5/7 分项通过；另外两项依赖 commit 存在。它们是保留的环境受限结果，不是主比较中的模型失败：
