# 跨上下文续接任务：NoteBatch

`fixtures/handoff/` 在两次独立模型进程之间复用同一工作树，检验阶段范围控制及剩余目标、接口约定的持久化。没有读取任何技能版本或候选输出。约 70 行初始 Python 和 README 内容，无网络和第三方依赖。

## 实验流程

1. 与既有夹具一样复制 `source/` 到独立工作树，初始化恰好一个 Git 提交。不要把两个 prompt、隐藏验证器、自检记录或本文件放进工作树。
2. wave1 只提供 `prompt1.txt`。其用户请求公开完整两阶段目标，要求今天完成基础归一化并自行留下明天全新任务继续所需信息，明确今天不实现 CLI 扩展。不指定笔记文件名、格式、字段或技能术语。
3. wave1 结束后保存完整工作树与工具轨迹快照；在外部运行 `validate_phase1.py WORKSPACE`。可另运行完整 `validate.py` 记录提前完成阶段 2 的情况，但其输出不应提供给 wave2。
4. wave2 用相同模型和同等权限启动全新进程，唯一业务请求是 `prompt2.txt`：继续上次剩余工作，按已确定的约定完成。复用 wave1 的全部工作树，包括未跟踪文件；不传递 wave1 对话、最终报告或工具日志。不要在 wave2 注入对照实验的本任务答案或概述。
5. 在外部运行 `validate.py WORKSPACE`，同时审查 wave1 是否遵循了阶段边界、留下什么信息，wave2 是否通过文件找回约定。不得把第一次请求文件偷偷留在新进程可读的目录里；模型自行选择记录完整请求属于有效保留。

manifest 沿用 `id/source/prompt/validator/dirty_files/expected_paths`，额外提供 `phases` 数组明确两个 prompt 和各自验证器。`prompt` 默认指向 wave1，执行器必须显式处理两阶段。所有验证器输出 `{checks: {name: bool}, details: {...}}`，全部通过退出 0，否则退出 1。

## 契约与判据

阶段 1 是小型真实修复：标题清洗，标签去空格、去空值、去重排序，校验错误统一为 ValueError，保留旧公开 API 和文件 CLI，且不修改调用方输入。

阶段 2 的真实消费端约定只在 wave1 用户请求中出现：

- `-` 作为 stdin 输入，文件和 stdin 共用 JSON 数组归一化。
- `--format json|jsonl`，默认 JSON 数组；JSONL 紧凑输出、Unicode 原字符、末尾换行，空批次零字节。
- `--unique` 使用清洗后标题的 `casefold()`，保留首次对象及顺序，不合并标签，默认不去重。
- 输入错误退出 2、stdout 为空、stderr 以 `input error:` 开头且无 traceback，禁止后部出错时输出前半批。

隐藏验收使用不同具体数据运行 API 和子进程 CLI，不以任何笔记文件名、说明措辞或规划格式评分。phase1 验证器检查基础实现；保留信息是否足够主要由新上下文 wave2 能否完整实现约定来验证。文档、回归测试内容质量和实际测试执行过程需通过轨迹及产物人工检查。两个阶段均不要求也不允许额外 Git 提交。

## 局限与解释

- 基础验收通过并不证明 wave1 保留了约定。应分别报告阶段 1 实现通过、剩余约定记录质量、阶段 2 完整通过，不能只看一个总分。
- phase1 验证器不扫描笔记内容，也不自动禁止提前实现阶段 2。若 wave1 越界做完后续功能，完整验收可能通过，但这不能算作成功的跨上下文续接；必须按轨迹单列为阶段范围违约。
- 如果 wave2 没有任何可恢复信息而选择询问用户，最终行为验收会失败。这表明两阶段链条未完成，不能据此把合理的澄清行为本身判成错误。
- 任务很小，一份普通的 README 笔记就可能足够。它测试最小的工作交接价值，不代表大型多代理编排、复杂冲突处理或长时间服务运维。
- 标准 CLI 习惯可能使模型猜中部分约定，但 casefold、首次对象不合并、精确 JSONL 与错误输出等组合降低纯猜测全通过的可能。仍应读取文件访问轨迹确认恢复来源，不能只靠分数归因技能。
- 一组任务不能证明某种技能全面更优；应保持三条件使用相同模型、相同阶段时限、相同上下文隔离方式，并记录 token 不可用为 unknown。
