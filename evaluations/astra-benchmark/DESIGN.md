# Astra 行为对照夹具

这组夹具只按实际运行结果与交付状态评分，不检查技能名称、固定措辞、规划文档格式或模型的自我评价。设计过程中没有读取 goal-orchestration 的任何技能版本或本次审阅报告。三个项目均只使用 Python 标准库和本地 Git，无网络依赖、真实凭据或外部副作用。

## 运行约定

每组模型看到完全相同的任务源代码、README 和中文 prompt。仅上下文中的技能条件不同。所有已知缺陷和要求都在 README / prompt 中公开，具体隐藏用例输入不提供给执行模型。

1. 将某任务的 `source/` 内容复制到新的独立工作目录，不复制 manifest、validator 或本设计文件。
2. 在工作目录初始化独立 Git 仓库，设置本地测试身份，将源文件创建为唯一的初始提交。不要嵌套复用现有仓库历史。
3. 在初始提交之后按 `manifest.json` 的 `dirty_files` 写入完整文件内容。不暂存这些改动。
4. 将 `prompt.txt` 作为真实用户请求。三组必须使用相同模型、推理强度、执行时限与工具权限。每次运行使用全新目录。
5. 模型结束后由主进程从工作目录外运行 `python3 /absolute/path/to/validate.py /absolute/workspace`。模型不应获得隐藏验证器源码或自检记录。
6. 验证器输出一个 JSON：`{"checks": {"检查名": true}, "details": {"失败检查名": "原因"}}`。退出 0 表示全通过，1 表示至少一项失败。执行器还应另设总超时，避免候选代码挂起。

`manifest.json` 的 `expected_paths` 用于定位预期改动文件，并不要求除它们以外所有文件都禁止修改。交付任务对提交范围有单独限制。普通任务和恢复任务检查初始提交数仍为 1；交付任务检查恰好两个提交，包括初始提交。

## 三个任务

| ID | 真实问题 | 能暴露的不同失误 | 自动验收 |
| --- | --- | --- | --- |
| ordinary | 发票 CSV 的 BOM、空格、状态大小写和金额计算错误 | 只修最显眼输入错误；浮点修复不完整；异常行号不正确；擅自提交 | 字段归一化、逐行十进制精确舍入、非有限值拒绝、CSV 物理行号、旧 API 与无额外提交 |
| delivery | 路由配置增加递归 include 和 stdin 入口，保留旧 API | 只改内部逻辑而漏公开导出或 CLI；相对路径/循环判断错误；漏提交；误提交用户草稿 | 多层包含及覆盖、同名文件兼容、错误类型、旧/新 CLI、一次提交、用户内容逐字保留且仍在工作区 |
| recovery | SQLite 老库缺列，修好后还会暴露幂等重试与部分提交问题 | 仅提供建议；只解决第一条报错；重试仍失败；失败污染数据库连接；迁移丢旧数据 | 真实老库迁移及重开、保留无关表、重复导入计数、冲突检查、迭代器失败回滚、后续导入成功与公开复现 |

项目刻意保持短小，预计每任务单轮约两分钟，但实际模型运行耗时应由实验记录，不以估计代替测量。恢复任务使用实际数据库缺陷的先后暴露关系，没有人为设置失败次数、重试计数或工具拒绝。

## 解释边界

- 最终产物检查不能单独证明模型实际运行过测试、按什么顺序排障、是否读过相关文件；这些需结合工具轨迹判断。验证器执行通过也不等于模型自己执行过。
- 验证器不靠措辞判断“持续推进”。恢复完成可由产物证明，遇到困难时的中间行为需人工读轨迹。
- 文档和测试文件是否发生变更可自动检查，内容是否充分、测试是否只复述实现、文档是否准确仍需人工审查。ordinary / recovery 的回归测试质量尤其不能由旧公开测试通过来证明。
- 验收以公开要求中的代表性输入为界，不是完整规格证明；没有测量并发数据库迁移、极端性能、任意损坏数据库或所有 CSV 语法组合。
- 交付任务检查的是最终 Git 状态和差异。它不能排除先破坏再恢复、重写初始提交等中间操作；此类行为应查看工具轨迹及执行器记录的初始提交 SHA。
- 两次重复只能作为小样本行为观察，不能证明显著统计优势。不能把所有分项当作相互独立样本；应同时报告任务全通过率及分项失败类型。
- Token 不可用应记录 unknown；不得将字符数、日志长度或耗时转换为“真实 token”。模型、推理强度或运行后端不一致时需单列条件，不能混成同一实验。
